\section{Benchmark and Experimental Setup}
\label{sec:setup}

\subsection{Tasks}
We build directly on \textsc{ParEval}~\cite{pareval}, the standard benchmark for
LLM-generated parallel code. We reuse its function-completion prompts, its
randomized-input drivers, and---most importantly---its \emph{serial reference}
implementations as the trusted answer $R_t$ we compare against. We pick the OpenMP tasks
whose result actually depends on how the work is split up: histograms (many threads
writing shared bins), reductions (does the combine step care about order?), scans (each
step depends on the last), and searches (which matching element you return depends on
order). These are the hazard classes of Table~\ref{tab:hazards}. Each prompt states what
to compute and the function signature, but never says how to parallelize it---so the model
has to choose a race-free, order-correct approach on its own.

\subsection{The Trusted Answer}
Correctness is judged by \textsc{ParEval}'s own driver: for each generated function it
compiles the model's code together with the serial reference, feeds both the same random
inputs, and checks whether their outputs agree. Because the reference is a plain sequential
program, it is immune to the parallel bugs we are hunting, so it makes an honest oracle;
and because we test on many random inputs, a program cannot squeak by on one lucky example.

\subsection{The Differential Verifier}
The new piece of our harness is a \emph{distribution-aware differential verifier}. Instead
of checking a program once, it compiles the code with OpenMP and runs it across a sweep of
thread counts $\tau\in\{1,2,4,8\}$, several times at each count, checking every run against
the serial reference. A program is robustly correct only if it matches at every thread
count and every repeat (Eq.~\ref{eq:R}). If the answer changes with the thread count, or
flickers between repeats at a fixed thread count, that is the fingerprint of a race or an
order-dependent bug, and the verifier reports it as not robust with a short diagnostic. The
repeats are what let it catch nondeterministic races that a single run---\textsc{ParEval}'s
default, and an ordinary agent's run-it-once signal---can miss. Compiling and running happen
on a dedicated multi-core cloud machine; the verifier, the prompts, and the per-run
transcripts are all released.

\subsection{Models}
We evaluate \Nmodels{} strong instruction-tuned models from one provider: a current
frontier general model, its previous generation, a code-specialized model, and a
higher-reasoning ``pro'' variant---all reached through Azure AI Foundry with Entra ID
auth and no stored API keys. Keeping the benchmark, harness, and prompts fixed, this
one-provider panel spans capability and specialization while controlling for
provider-specific style: an effect (or its absence) that holds across all \Nmodels{}
models, including one tuned specifically for code, is unlikely to be a quirk of a single
weak or odd model. The harness is model-agnostic---it reaches any deployment through one
uniform API---so we also add an \emph{open-weights} panel of \NopenModels{} models served
on a research cluster (from a 120B general model down to a 27B one), which we run on the
race-prone tasks to see how the verifier's value changes with capability
(Section~\ref{sec:crosscap}); a broader cross-vendor sweep is future work
(Section~\ref{sec:discussion}). In the baseline condition the model simply gets the prompt
and returns a completion, which the harness compiles and checks as-is. Every generation---
system prompt, user prompt, raw response, extracted code, and verifier feedback---is logged.

\subsection{The Controlled Swap}
To ask what the differential verifier is really worth, we run the \emph{same}
propose--observe--repair agent at three tool levels---L0 (no tool), L1 (run once at one
thread), L2 (the full thread-sweep verifier)---holding the model, prompt, and repair budget
$B$ fixed and changing \emph{only} the checking tool (Fig.~\ref{fig:pipeline}). The agent
writes the function, the tool returns an observation, and---for L1 and L2---the agent
repairs on failure until the tool passes it or the budget runs out. Whatever the condition,
the \emph{final} program is always scored by the full differential verifier over the
complete sweep, an outcome measure that does not depend on which tool the agent was allowed
to use. Every repair round---the feedback and the revised program---is logged, so the whole
trajectory is auditable.
