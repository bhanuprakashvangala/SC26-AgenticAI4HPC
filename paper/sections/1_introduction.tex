\section{Introduction}

AI agents now write a lot of the parallel code that HPC runs on. They refactor old
kernels, port code between programming models, and glue together the data stages between
simulation, analysis, and machine learning~\cite{agentic_hpc}. And increasingly they
\emph{check their own work}: the agent writes a program, runs a checker, and ships
whatever passes. The same checker is doing double duty elsewhere, too. The newest models
are trained by reinforcement learning in which an automatic checker---not a human---hands
out the reward~\cite{rlvr,grpo}. In that setting a piece of work is only accepted, and the
reward is only paid, once the checker says so; this is the idea behind
\emph{verification-guided} post-training, where an execution check ends a stage of work
and scores it~\cite{options}. Either way---as an agent's accept/reject gate or as a
training reward---that checker \emph{is} the working definition of ``good'' parallel code.
So the real question is about the checker: \emph{what does it need to measure before we
should trust, or train toward, the parallel code an agent writes?}

Parallel code makes this hard for two reasons. First, whether a parallel program is
correct is a whole-execution property, not a local one. The answer can depend on how many
threads or partitions run it, whether some step has to happen in order, and how the pieces
are combined at the end---none of which is visible in the stream of tokens the model is
looking at. This is not a hypothetical worry: models are much less reliable on parallel
code than on the serial version of the same task~\cite{pareval}, and the parallel code
they write often hides races. Second---and this part is specific to \emph{agents}---an
agent that checks itself by running the code \emph{once} sees that it ran and produced a
sensible answer, and concludes it is correct. But a concurrency bug does not have to show
up on any single run. The very signal an agent trusts to verify itself can be blind to the
bugs that only appear when you change the configuration.

A small example makes this concrete. Ask an agent to build a histogram---count how many
values fall into each bin. It writes an OpenMP loop in which every thread bumps a shared
bin counter, runs it once, sees a reasonable histogram, and submits. The program is wrong:
two threads update the same counter at the same moment, and one of the updates is lost to
a data race. But on a \emph{single} thread there is nobody to collide with, so the answer
is exactly right; and even on several threads the few lost counts can look fine. Nothing
in a single run reveals the bug---not to a developer who ran it once, and not to an agent
whose only tool is to run it and look at the output. The check that was performed is blind
to the bug, and a reward computed from that check would happily certify it.

We call the property a good check should establish \emph{configuration-robust
correctness}: a program counts as correct only if it matches a trusted serial reference
under \emph{every} configuration we try---each thread count, run more than once---not just
the one configuration that happened to be tested. The interesting quantity is the
\emph{gap} between what a single ordinary run sees and this robust notion: programs that
sit in that gap pass the cheap check but are not actually robust. That gap is the surface
where silent bugs live, and for an agent it is \emph{actionable}---the right checking tool
can expose it.

But a check that is going to be \emph{optimized}---by an agent's repair loop, or by an RL
training objective~\cite{rlvr,grpo}---can fail as a specification in two different ways,
and both drive this paper. It can be \emph{saturated}: if the models already pass it, a
sharper correctness check has nothing left to add, and effort spent making the check finer
is wasted. And it can be \emph{gameable}: if the highest score is reachable by a degenerate
answer, then whatever is optimizing the check will drift toward that answer. We find that
the natural correctness check for parallel code has \emph{both} problems at the frontier.
The saturation is empirical: today's self-repair loops~\cite{selfdebug,reflexion,lassi}
run on a single-configuration signal that is, in principle, blind to races---yet swapping
in a sharper signal that is \emph{not} blind changes nothing, because the strong models
rarely write the bug. The gameability is structural: correctness is a property of the
output, and a program with every parallel construct deleted---plain serial code---matches
the reference at every thread count, so the check is \emph{maximized} by code that does not
run in parallel at all. The fix follows the same verification-guided logic: pair the
correctness check with a second checked stage---a \emph{performance} gate that ends not
when the answer matches but when the code actually gets faster---so the reward an agent or
an RL loop optimizes measures two things, correct \emph{and} parallel. This paper builds
the evidence for that gate; building and training it is the natural next step
(Section~\ref{sec:discussion}).

We answer with an open, reproducible study built on \textsc{ParEval}~\cite{pareval}, the
standard benchmark for LLM-generated parallel code. A tool-using agent writes OpenMP code
and can call a small toolbox: compile and run a draft at one thread count, or
\emph{differentially verify} it across a sweep of thread counts with repeats against
\textsc{ParEval}'s serial reference. Compiling and running happen on a real multi-core
machine. We run the agent with several strong models and, in a controlled swap, take the
differential checker away to see exactly what it was worth; the final score always comes
from an independent full-sweep check, so the outcome does not depend on which tool the
agent was allowed to use. Then, holding correctness fixed, we measure the second axis the
check ignores---how much faster the accepted code actually runs.

\noindent This paper makes five contributions.
\emph{First}, we frame the design of the checker an agent accepts on---which is also the
reward an RL loop would optimize---as the central reliability question, and name the two
ways it can fail: \emph{saturation} and \emph{gameability} (Section~\ref{sec:metric}). We
define \emph{configuration-robust correctness} and the gap between it and ordinary
single-run correctness as the correctness axis of that checker.
\emph{Second}, we build the differential verifier and hand it to a tool-using agent that
writes and repairs parallel code, and we release the harness, tasks, prompts, the two-axis
scorer, and full agent transcripts, in line with the SC26 reproducibility initiative
(Sections~\ref{sec:metric}--\ref{sec:setup}).
\emph{Third}, we run the agent with strong models on ParEval's OpenMP tasks and find the
correctness signal \emph{saturated}: single-shot generation is already robustly correct
\Lzerorate{} of the time, a repair loop raises this to \Lonerate{}, and the full
differential verifier leaves it unchanged at \Ltworate{}, with Wilson confidence intervals
throughout (Section~\ref{sec:results}).
\emph{Fourth}, our controlled swap gives a \emph{clarifying negative} result: for
\Nmodels{} strong models on standard OpenMP tasks, the differential verifier does not beat
a single-thread check, because these models rarely write the silent race it targets---their
mistakes are ordinary and already visible on one thread---so it is the \emph{repair loop},
not the checker's thread-sweep, that drives the gain over single-shot. Injected races, an
independent race detector (Archer), and an open-weights panel---where a smaller model does
ship a real race the verifier catches and fixes---bound the checker's value: it grows
exactly as model capability falls (Sections~\ref{sec:results}--\ref{sec:discussion}).
\emph{Fifth}, and most important, we show the correctness check is \emph{gameable}---a
serial program scores perfectly---and then measure the second axis directly: the programs
the check accepts run from $0.33\times$ to $7.9\times$ on eight threads, one of them
\emph{slower} in parallel than serially. Once strong models make race-freedom cheap, any
accept/reject gate or training reward for HPC code has to score \emph{both} axes---correct
\emph{and} actually parallel---because ``correct but not parallel'' is where this code now
fails, and a check that looks only at the output cannot see it. We argue for a two-axis
reward with a correctness-guarded performance gate, and show on our own data that selecting
programs by correctness alone throws away large speedups a two-axis reward keeps
(Section~\ref{sec:scaling}, Section~\ref{sec:discussion}).
